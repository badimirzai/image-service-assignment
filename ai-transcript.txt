## 2. Proposed implementation strategy

### Your layered shape is good — keep it thin

```
handlers  →  service  →  storage interface  →  memory / later sqlite
```

**Challenge / simplification:** For this assignment size, avoid a heavy “domain layer,” DTOs everywhere, or repository + unit-of-work. Prefer:

- **`internal/httpapi`** (or `handlers`): parse HTTP, status mapping, headers  
- **`internal/images`**: create/update/get/list/crop/batch orchestration, validation, concurrency  
- **`internal/store`**: interface + memory (+ optional sqlite)

The service owns: decode/validate image, derive metadata, bbox crop, batch worker pool + ctx cancel.  
Storage owns: durable/ephemeral persistence of `{id → bytes + metadata}` only.

**Do not abstract:**
- Image decoding behind a plugin system  
- “Repository” separate from “Store”  
- Event bus / CQRS  
- Generic multipart framework  

**SQLite transition without ceremony:**

1. Define a small store interface early, e.g. conceptually:  
   `Create`, `Update`, `Get`, `GetData`, `List`  
   (signatures take `context.Context`; return typed errors like `ErrNotFound`)
2. Memory impl: `sync.RWMutex` + map  
3. Later SQLite: same interface; one table with `id`, metadata columns, `blob`; transactions per write  
4. Wire in `main` via constructor — **no factory registry**  
5. Handlers/tests stay on the interface; add a few SQLite integration tests if you add it  

**When the interface is unnecessary:** If you truly only ever ship memory, you could skip the interface and still pass. Given you want a possible SQLite swap, a **4–6 method interface** is the right amount of abstraction—not over-engineering.

**Better simpler alternative?** Single package with handlers calling a `MemoryStore` directly is fine for a tiny demo, but you already want the swap path and clear tests. The thin interface wins.

**Blob in SQLite:** Fine for assignment scale. Document that production would use S3/GCS + DB metadata. Don’t build that now.

## 3. Trust boundaries and validation

### What comes from the request

| Source | Trust? |
|--------|--------|
| Raw body bytes (`POST`/`PUT`) | Untrusted; decode + size-limit |
| `Content-Type` header | Untrusted hint only |
| Path `id` | Untrusted; validate format (UUID); lookup |
| `bbox` query | Untrusted; parse + bounds-check |
| Multipart parts (filename, part Content-Type, bytes) | Filename only for error reporting; type from bytes |

### Must validate

- Body non-empty and within max size  
- Bytes decode as supported image  
- `id` well-formed and exists where required  
- `bbox`: 4 ints, `w>0`, `h>0`, region ⊆ image  
- Batch: part count ≤ max; each part same per-image rules  
- Multipart Content-Type for batch endpoint  

### Derive from bytes (not client)

- Format (`jpeg`/`png`/`gif`) via decode config / format sniff  
- Width, height from decoded bounds  
- Filesize = `len(storedBytes)` (original upload bytes, not re-encoded)  
- `created_at` / `updated_at` = server clock  

**Prefer:** `http.MaxBytesReader` → read → `image.Decode` / `DecodeConfig` with format blank-imports. `DecodeConfig` can get dimensions + format without full decode for metadata-only paths; for store-and-serve you still need the original bytes. Validate with decode (or DecodeConfig + verify); store **original bytes**, not re-encoded, so GET data is bit-stable.

### Reject as malformed

- Empty body  
- Oversized body  
- Undecodable / unsupported format  
- Invalid UUID / unknown ID (different statuses)  
- Malformed or OOB bbox  
- Batch not multipart / too many parts / empty batch (decide: empty batch → 400)

### Size limits

- Wrap body with `MaxBytesReader` at handler edge  
- Optionally also check `Content-Length` early (still enforce on read—clients lie)  
- Batch: limit total request size and/or per-part size  

### Status mapping (classes)

| Failure | Status |
|---------|--------|
| Bad JSON/query/bbox parse, empty body, invalid image, unsupported format, empty batch | **400** (or **415** for clearly wrong media type on batch/non-image—see §4) |
| Unknown ID | **404** |
| Body too large | **413** |
| Wrong Content-Type for batch (not multipart) | **415** |
| Unexpected store/panic-level failure | **500** |
| Success GET/list | **200** |
| Success POST create | **201** |
| Success PUT | **200** (or 204 with no body—prefer **200 + metadata** for symmetry) |

## 4. HTTP semantics

| Code | Use when |
|------|----------|
| **200** | List; get metadata; get image data; successful PUT; batch completed (including partial success) |
| **201** | Single image created (`POST /v1/images`) |
| **400** | Validation errors (bbox, empty, undecodable image, bad id format if you don’t use 404 for that) |
| **404** | ID not found |
| **413** | Exceeds max bytes |
| **415** | `POST /batch` without `multipart/form-data`; optionally single upload with clearly non-image Content-Type *before* reading—bytes still win if you sniff; don’t overuse 415 |
| **500** | Bugs / unexpected storage errors only |

**Practical 415 vs 400:**  
- Unsupported *image format* after sniff → **400** (body was understood as “try to upload image,” content invalid)  
- Endpoint expects multipart, got `application/json` → **415**  

### Headers

| Response | Headers |
|----------|---------|
| Metadata JSON | `Content-Type: application/json` |
| Image bytes | `Content-Type: image/jpeg\|png\|gif`, `Content-Length` |
| Create | `Location: /v1/images/<id>` + JSON body with metadata |
| Errors | `Content-Type: application/json` |

### Error JSON (keep minimal)

```json
{"error":"image too large"}
```

Batch:

```json
{
  "images": [ /* metadata objects */ ],
  "errors": [ { "name": "a.png", "error": "unsupported format" } ]
}
```

Even when some fail, **200** with both arrays is the right partial-success pattern (not 207 unless you want WebDAV theater—skip 207).

### Other useful semantics

- Don’t set entity tags / caching unless you want a small `ETag` from content hash—optional, not required  
- Propagate context cancellation on batch  
- No redirect tricks

## 5. Architecture options

### Option A — Minimal monolith (simplest)

**Components:** `main` + one `handlers.go` + `store.go` (memory map)  
**Flow:** Handler validates → writes map → responds  
**Complexity:** Lowest  
**Testability:** Good with `httptest`  
**Scalability:** Process-local only  
**Tradeoffs:** Batch/crop logic tangled in handlers; SQLite swap messier  
**Failure modes:** Fat handlers; hard to test cancel/concurrency in isolation  

### Option B — Thin service + store interface (recommended)

**Components:** `cmd/server`, `httpapi`, `images` (service), `store` (interface + memory [+ sqlite])  
**Flow:** HTTP → service (validate, decode, crop, batch) → store  
**Complexity:** Low–moderate; clear seams  
**Testability:** Service tests without HTTP; store tests without HTTP; handler tests thin  
**Scalability:** Same process limits; documented upgrade path  
**Tradeoffs:** Tiny bit more wiring  
**Failure modes:** Over-abstracting the interface (resist)  

### Option C — “Production-oriented”

**Components:** B + config package, middleware metrics/logging, migrations, object storage interface, OpenAPI, graceful shutdown orchestration  
**Complexity:** High for a take-home  
**Testability:** Excellent but slow to build  
**Scalability:** Better story on paper  
**Tradeoffs:** Looks padded; more to break  
**Failure modes:** Incomplete glue, evaluator fatigue  

### Recommendation: **Option B**

It shows production judgment (boundaries, testability, cancel/concurrency in the service) without resume-driven architecture. Document how you’d scale (blob store, metadata DB, horizontal API) in the README—that satisfies the brief’s “motivated less ideal choice” clause.

Your pool design is sound. The edge cases worth designing for up front:

**1. Cancel ≠ per-item failure**  
Only `r.Context()` cancellation should stop the pool. A bad image is a per-item error; other workers should keep going. If you wire “first error cancels everything,” you break partial success.

**2. What cancel can and cannot interrupt**  
Cancel should stop **taking new jobs** and skip **store writes** once `ctx` is done. `image.Decode` is generally not abortable mid-call—one in-flight decode may finish. That is acceptable; the requirement is “don’t keep unnecessary work running,” not hard-preempt CPU.

**3. Orphan creates after disconnect**  
Work that already passed validation may still `Create` unless you check `ctx` immediately before the store write. Even then, successfully stored images before disconnect usually **stay** (compensating deletes are not worth it here). Document that; don’t build rollback.

**4. Bound memory, not only goroutines**  
A pool caps CPU concurrency; it does **not** cap memory if you first load every multipart part into `[]byte`. Cap **batch count** and **per-image size** (and multipart total size). The pool and the size limits solve different problems.

**5. Don’t leak workers; write the response once**  
`WaitGroup`/`errgroup`-style wait so handler return doesn’t leave goroutines behind. Aggregate results (by index) under a mutex or via a results channel, then write JSON **once**. On disconnect you often cannot send that body—cancellation is still doing its job by stopping work.

**6. Preserve input identity in errors**  
Record failures with part index and/or filename so the partial-success response stays usable under concurrency.

Skip: per-image transactions spanning the batch, cancel-driven cleanup, and dynamic pool sizing. Fixed pool + shared request `ctx` + per-item errors is enough.

## Service — what I’d change before calling it done

### 1. Cancel + `results` channel (important)

On cancel, the **dispatcher** pushes synthetic errors for remaining indices **into `results`**, while **workers** may still push for jobs already taken. You can get **duplicate idx** or, worse, **block** if `results` fills (`buffer = len(items)`) while workers and dispatcher both send and the consumer isn’t keeping up in an edge timing.

Safer pattern: only workers write to `results`; on cancel, close `jobs`, workers exit, and for any index with no result yet, mark cancelled in the main goroutine after the pool drains. Or use a `[]result` with mutex, one slot per index.

### 2. Skip store write on cancel

`CreateFromBytes` does not check `ctx` before `store.Create`. Workers only check before calling it — once decode starts, a disconnect can still **commit**. Checking `ctx.Err()` immediately before `Create` better matches “skip writes when cancelled.”

### 3. Small cleanups (optional)

- Unused `ErrBatchTooLarge` vs `ErrBatchTooManyImages` — keep one.  
- Consider `index` on `BatchItemError` (filename alone can collide).  
- No batch tests yet — add after the handler exists.
